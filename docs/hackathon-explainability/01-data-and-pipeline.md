# 1. Where the data comes from and how the pipeline works

## Data source

GuardianSync uses a hybrid data pipeline:

1. Synthetic SCADA-style telemetry is generated locally in the AI engine for training.
2. Real-time simulated packets are generated by the backend during the demo.
3. The AI engine receives those packets and returns an anomaly decision.

### Training data

The training data is created in [ai-engine/app/train.py](ai-engine/app/train.py) by calling:

- [ai-engine/app/simulator.py](ai-engine/app/simulator.py) to generate normal readings
- [ai-engine/app/attack_generator.py](ai-engine/app/attack_generator.py) to generate attack-like readings

This process produces two classes:

- Normal readings with label 0
- Attack-style readings with label 1

The generated dataset is saved in [ai-engine/data](ai-engine/data), including:

- training_dataset.csv
- normal_stream.csv
- attack_stream.csv

### Runtime data

At runtime, the backend simulation service in [server/src/services/packetBroker.js](server/src/services/packetBroker.js) creates packets representing SCADA events. These packets include:

- a command such as READ_SENSOR or OVERRIDE_SAFETY
- a target machine
- an industry profile
- a set of numerical parameters such as temperature, pressure, flow rate, and network latency

The backend sends these packets to the AI engine through the service client in [server/src/services/aiClient.js](server/src/services/aiClient.js).

## End-to-end flow

The full workflow is:

1. The simulator creates a packet.
2. The backend emits it live to the UI.
3. The AI engine receives the packet parameters.
4. The model checks for hard safety limits.
5. The main anomaly model computes a score.
6. A decision is returned: PASS or BLOCK.
7. The backend logs the result and optionally creates alerts.

## Why this data design is appropriate

This project is designed for a hackathon demonstration, so the data is intentionally:

- structured and tabular
- interpretable by humans
- fast to compute
- easy to explain in a live demo

This makes it ideal for a small, explainable ML model instead of a black-box LLM system.

## What the data looks like

The input vector contains 14 engineered features:

- temperature
- pressure
- flow_rate
- voltage
- current
- rpm
- vibration
- humidity
- power_consumption
- response_time
- packet_size
- command_frequency
- error_rate
- network_latency

These are defined in [ai-engine/app/utils.py](ai-engine/app/utils.py).

## Practical interpretation

Each packet is treated as a snapshot of industrial behavior. The model asks:

- Is this snapshot consistent with normal industrial operations?
- Does it show signs of tampering, flooding, or unstable conditions?

That is why the system is best viewed as a real-time anomaly detector for operational technology, not as a general-purpose chatbot.
